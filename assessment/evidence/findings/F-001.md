# F-001 | P1 | BUILT-WRONG | auth / tenant isolation

**Impact:** An authenticated admin of one tenant can mint a JWT for *any other* tenant by setting the `X-Tenant-Scheme` header at login, then read and write that tenant's data. Tenant isolation — the platform's core security property — is bypassed with a header.

**Repro (local, dev DB):**
```bash
# 1. login as the SAME admin, only the header differs
curl -s -X POST http://localhost:3001/api/v1/auth/login \
  -H 'Content-Type: application/json' -H 'X-Tenant-Scheme: acme' \
  -d '{"email":"admin@example.com","password":"password123"}'
curl -s -X POST http://localhost:3001/api/v1/auth/login \
  -H 'Content-Type: application/json' -H 'X-Tenant-Scheme: test-corp' \
  -d '{"email":"admin@example.com","password":"password123"}'
# 2. GET /assessments with each token
```

**Observed** (full output in `evidence/findings/F-001-repro.txt`):
- `X-Tenant-Scheme: acme` token → `{"assessments":[{"name":"Acme Senior Engineer", ...}], "meta":{"total_count":1}}` (tenant B data)
- `X-Tenant-Scheme: test-corp` token → `{"assessments":[], "meta":{"total_count":0}}` (tenant A data)

Same user, same password — only the header changed — and the token is scoped to a different tenant.

**Expected:** The `scheme` claim in the JWT must be the user's own tenant, validated server-side. A user must not be able to select an arbitrary tenant at login.

**Root cause:** `authentication_controller.rb` `resolve_scheme` takes `request.headers['X-Tenant-Scheme']` with no ownership check (`api/app/controllers/api/v1/authentication_controller.rb:24-29`); compounded by the tenant resolver reading `scheme` from an *unverified* JWT (`api/app/middlewares/tenant_resolver_middleware.rb:42-51`).

**Caught by:** planned — RSpec request spec asserting the scheme is derived from the user's org, not the request header.

**Status:** open
